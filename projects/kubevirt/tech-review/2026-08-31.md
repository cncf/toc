# General Technical Review (Reviewer Assessment): KubeVirt / Graduation

- **Project:** KubeVirt
- **Reviewed version:** v1.9.0 (GA 2026-07-30, following v1.8.4)
- **Website:** https://kubevirt.io
- **Date of this review:** 2026-08-31
- **Template version:** v1.0 ([toc_subprojects/project-reviews-subproject/general-technical-questions.md](../../../toc_subprojects/project-reviews-subproject/general-technical-questions.md))
- **Reviewer role:** TOC/TAG technical reviewer, independent verification for Graduation Due Diligence ([cncf/toc#1822](https://github.com/cncf/toc/issues/1822))
- **Inputs:** the project's own self-GTR (kubevirt/community/CNCF/general_technical_review.md, merged 2025-01-24, project version 1.4), the cncf/toc#1822 application text, kubevirt/kubevirt and kubevirt/community at `main`, kubevirt/sig-release, the GitHub Releases API for kubevirt/kubevirt, and the published TAG-Security self-assessment at tag-security.cncf.io.

## Summary and Assessment

**Status:** Satisfactory, with open follow-up items

KubeVirt's engineering fundamentals (API versioning discipline, release
engineering, the Kubernetes compatibility policy, and the VEP-driven
roadmap) are solid and independently verifiable against primary sources.
That said, a few concrete items should be resolved or explicitly acknowledged
before Graduation sign-off.

## Day 0: Planning Phase

### Scope

**Q: Describe the roadmap process, how scope is determined for mid to long term features, as well as how the roadmap maps back to current contributions and maintainer ladder.**

The roadmap runs through the Virtualization Enhancement Proposal (VEP)
process in [kubevirt/enhancements](https://github.com/kubevirt/enhancements), tracked
on a public board and mirrored in a continuously-updated pre-release-notes
doc ([upcoming-changes.md](https://github.com/kubevirt/sig-release/blob/main/upcoming-changes.md)).
The v1.9.0 release notes cite specific VEP numbers against merged work
(VEP-10, VEP-160, VEP 250, VEP-190), confirming the process drives real
feature decisions rather than existing only as documentation. The
self-GTR's claim that the roadmap ties into the maintainer ladder is not
verifiable from the outside; I found no maintainer promotion tied
directly to VEP ownership, though this is not a blocker.

**Q: Describe the target persona or user(s) for the project.**

Infra owners, platform engineers, and DevOps teams
running mixed VM/container workloads through the standard
`VirtualMachine`/`VirtualMachineInstance` CRDs.

**Q: Explain the primary use case for the project. What additional use cases are supported by the project?**

Primary use case (bridging legacy VM
workloads and containerized ones under one control plane) and the
additional use cases listed in the self-GTR (infra modernization, hybrid
architectures, CI/CD test environments, edge, isolation, multi-tenancy)
all check out against the adopter list, for example CoreWeave and Genesis
Cloud for GPU/edge-adjacent use, Killercoda for ephemeral learning
environments.

**Q: Explain which use cases have been identified as unsupported by the project.**

No multi-hypervisor abstraction beyond KVM/QEMU,
no cross-cloud ("Delta Cloud"-style) API abstraction, and that's still
accurate as of v1.9.0. Newer work like the MSHV backend and the alpha
`CrossArchitectureVirtualization` gate expand what's possible without
contradicting this stated boundary.

**Q: Describe the intended types of organizations who would benefit from adopting this project.**

No specific vertical targeting; the project
correctly frames itself as broadly applicable given how ubiquitous
virtualization is across industries. The adopter list backs this up,
covering everything from telecoms (Swisscom, Aussie Broadband) to GPU
clouds (CoreWeave, Genesis Cloud, Nebius) to a child-safety nonprofit
(Child Rescue Coalition).

**Q: Please describe any completed end user research and link to any reports.**

None conducted formally, which the self-GTR admits
outright. Not blocking on its own. The [ADOPTERS.md](https://github.com/kubevirt/kubevirt/blob/main/ADOPTERS.md) breadth (40+
organizations) and the TOC's own adopter-interview process substitute for
a project-run research program reasonably well, though it does mean the
project relies mostly on downstream vendors (Red Hat, SUSE) for direct
end-user UX feedback rather than running its own loop.

### Usability

**Q: How should the target personas interact with your project?**

Exclusively through
Kubernetes-native APIs/CRDs and `virtctl`; no separate control-plane
protocol.

**Q: Describe the user experience (UX) and user interface (UI) of the project.**

No first-party UI. `virtctl` (CLI) and the Kubernetes API/CRDs
are the only interaction surfaces the project itself maintains. Third-party
UIs exist downstream (SUSE Virtualization, OpenShift Virtualization
console, Deckhouse, the community KubeVirt Manager project), but none are
maintained by kubevirt/kubevirt. Consistent with the "KubeVirt Razor"
design principle, and not unusual for an infrastructure-extension project
at this maturity level.

**Q: Describe how this project integrates with other projects in a production environment.**

I checked a few of the claimed integrations
against actual evidence rather than taking the list at face value. The
shipped `kubevirt-operator.yaml` and docs include real
`PrometheusRule`/`ServiceMonitor` objects (not aspirational). The v1.9.0
changelog has ongoing work on network binding plugins consistent with the
claimed Multus integration, and the Velero integration is active in the
current release (an annotation to disable Velero hooks in `virt-launcher`
shipped in v1.9.0). This is one of the stronger parts of the application:
the integrations show up as ongoing code changes in recent releases,
rather than as a static list in a document.

### Design

**Q: Explain the design principles and best practices the project is following.**

The CRD-first, "if it's useful for Pods, don't
build a VM-only version" philosophy (the "KubeVirt Razor") is consistently
reflected in [`docs/architecture.md`](https://github.com/kubevirt/kubevirt/blob/main/docs/architecture.md) and [`docs/components.md`](https://github.com/kubevirt/kubevirt/blob/main/docs/components.md).
It's a real, distinctive design stance, not boilerplate.

**Q: Outline or link to the project’s architecture requirements. Describe how they differ for Proof of Concept, Development, Test and Production environments, as applicable.**

Still informal.
There's no structured sizing guidance beyond "roughly 1 CPU/1GB" for the control
plane, and no explicit differentiation between environment tiers. A
documentation gap worth flagging, but not unusual at this stage since
actual sizing is mostly driven by the underlying Kubernetes cluster rather
than KubeVirt itself.

**Q: Define any specific service dependencies the project relies on in the cluster.**

None mandatory beyond the Kubernetes API
server, confirmed by the installation manifests, which only add the
operator and a CR.

**Q: Describe how the project implements Identity and Access Management.**

Delegated entirely to Kubernetes RBAC;
no separate authn/authz layer is introduced. That's the right call, since
introducing a second authorization model would create a drift risk against
cluster RBAC.

**Q: Describe how the project has addressed sovereignty.**

Handled structurally through KubeVirt's independent
SIG/WG/Subproject governance, which operates separately from the
Kubernetes SIGs (confirmed in [GOVERNANCE.md](https://github.com/kubevirt/community/blob/main/GOVERNANCE.md) and [sig-list.md](https://github.com/kubevirt/community/blob/main/sig-list.md)).

**Q: Describe any compliance requirements addressed by the project.**

None pursued at the project level, which is
normal. Compliance certification is typically a vendor/distribution
concern (Red Hat, SUSE), not a project-level one.

**Q: Describe the project’s High Availability requirements.**

`virt-controller`, `virt-api`, and
`virt-operator` run as multi-replica Deployments with leader election in
the shipped manifest, and `virt-handler` is a DaemonSet, so node-level HA
follows from normal Kubernetes scheduling. The project's contribution to
Medik8s for bare-metal fencing/HA is a genuine upstream contribution,
consistently referenced across the security/HA docs.

**Q: Describe the project’s resource requirements, including CPU, Network and Memory.**

Reasonable but
incomplete. The "~1 CPU/1GB" figure covers the control plane only, not
the per-VM overhead of `virt-launcher` pods, which is documented elsewhere
but not surfaced in the GTR answer itself. Network requirements are
correctly described as inheriting Kubernetes' own.

**Q: Describe the project’s storage requirements, including its use of ephemeral and/or persistent storage.**

Fully delegated to Kubernetes storage
classes/CSI. KubeVirt doesn't implement its own storage layer, which
keeps its blast radius for storage bugs small.

**Q: Please outline the project’s API Design. Describe the project’s API topology and conventions.**

RESTful, declarative CRDs
following Kubernetes conventions, as claimed.

**Q: Describe the project defaults.**

The Operator ships with working defaults; a
`KubeVirt` CR with no spec is enough to get a functioning install.

**Q: Outline any additional configurations from default to make reasonable use of the project.**

Feature gates
(`spec.configuration.developerConfiguration.featureGates`, and as of
v1.9.0 the ability to opt out of individual Beta gates via
`disabledFeatureGates`) are the primary lever beyond defaults.

**Q: Describe any new or changed API types and calls, including to cloud providers, that will result from this project being enabled and used.**

All new surfaces are KubeVirt CRDs (e.g. the new
`plugin.kubevirt.io/v1alpha1` Plugin CRD in v1.9.0); nothing modifies
cloud-provider APIs directly.

**Q: Describe compatibility of any new or changed APIs with API servers, including the Kubernetes API server.**

Tracked in a dedicated, actively maintained [`docs/kubernetes-compatibility.md`](https://github.com/kubevirt/kubevirt/blob/main/docs/kubernetes-compatibility.md)
plus a support matrix in sig-release. Better documented than most CNCF
projects manage at this stage.

**Q: Describe versioning of any new or changed APIs, including how breaking changes are handled.**

This is one of
the stronger areas overall. The core `kubevirt.io/v1` API has been stable
and backward-compatible for years; newer/experimental surfaces correctly
start at `v1alpha1` behind feature gates instead of touching the stable
API. The Plugin CRD and the Template feature gate's alpha→beta promotion
in v1.9.0 are concrete, recent examples of this discipline being followed
in practice.

**Q: Describe the project’s release processes, including major, minor and patch releases.**

Also strong. [`docs/release.md`](https://github.com/kubevirt/kubevirt/blob/main/docs/release.md)
documents semver tagging, signed git tags, a schedule trailing Kubernetes
by ~2 months, and a maintenance window tied to upstream Kubernetes
support. This isn't aspirational: the GitHub Releases API confirms
v1.9.0 was published 2026-07-30 as "a promotion of release candidate
v1.9.0-rc.2... originally published 2026-07-28," matching the documented
RC→GA flow exactly.

### Installation

**Q: Describe how the project is installed and initialized, e.g. a minimal install with a few lines of code or does it require more complex integration and configuration?**

`kubectl apply` of an operator
manifest plus a `KubeVirt` CR, matching the "minimal install" claim, and
the v1.9.0 release assets include the exact manifests referenced in the
docs.

**Q: How does an adopter test and validate the installation?**

Via the project's own
e2e/conformance suite. A `conformance.yaml` asset now ships alongside
releases, which is a tangible, distributable validation artifact beyond
what most incubating projects provide.

### Security

**Q: Please provide a link to the project’s cloud native security self assessment.**

The self-GTR (Jan 2025) said
this was still "in progress" (tracked in kubevirt/community#335). A
self-assessment is now published at
[tag-security.cncf.io/.../kubevirt/self-assessment](https://tag-security.cncf.io/community/assessments/projects/kubevirt/self-assessment/),
the official TAG-Security and Compliance assessments site, and I read it
in full. It's reasonably substantive, covering actors
(virt-operator/api/controller/handler/launcher), the unprivileged
virt-launcher design, a long list of security-relevant configuration
items (restricting GPU/USB passthrough, disabling KSM, RBAC on migration
and exec access, VLAN segmentation, MAC spoof filtering), a Restricted
Pod Security Standard compliance claim, and branch-protection/PR-review
rules. **Its metadata table lists "Assessment Stage: Incomplete,"**
though, which contradicts the DD issue's claim that the self-assessment
"has been completed and published." This is a live discrepancy on the
project's own published page, not an artifact of stale archived content.
It should be confirmed directly with the project, and the metadata
either updated to reflect completion, or the DD issue's claim corrected,
before treating this Security Engineering Principle as satisfied.

**Q: How are you satisfying the tenets of cloud native security projects?**

VMs run as regular pods
under the cluster's PSA profile and gain no extra privileges over any
other workload, with elevated privileges scoped narrowly to `virt-handler`
(a necessary, node-level exception for device/cgroup access). The
published self-assessment backs this up with specifics: `virt-launcher`
(the VM host pod) is documented as non-root, has no SELinux policy
exception, and requires only the `NET_BIND_SERVICE` capability, and the
project asserts compliance with the Restricted Pod Security Standard.
That's a legitimate, and reasonably well-evidenced, secure-by-default
design.

**Q: How do you recommend users alter security defaults in order to "loosen" the security of the project? Please link to any documentation.**

The 2020 blog post ("KubeVirt Security Fundamentals") is still the
canonical link in most places. The published self-assessment's "Security
functions and features" section is a more concrete resource on this
question. It lists specific configuration knobs that trade security for
functionality (e.g. allowing GPU/USB host-device passthrough via
`spec.configuration.permittedHostDevices`, enabling KSM via
`spec.configuration.ksmConfiguration`, allowing shareable disks, or
leaving nested virtualization enabled), each with a one-line risk
explanation. This should be promoted as the primary "loosening"
reference over the 2020 post, but it isn't cross-linked from [SECURITY.md](https://github.com/kubevirt/kubevirt/blob/main/SECURITY.md)
or the blog post today, so a reader following the most commonly-linked
doc would still land on the older material.

**Q: Security Hygiene: please describe the frameworks, practices and procedures the project uses to maintain the basic health and security of the project.**

Concretely enforced: 2+
approvals per PR via [OWNERS_ALIASES](https://github.com/kubevirt/kubevirt/blob/main/OWNERS_ALIASES), DCO sign-off required in CI, 2FA
required by membership policy, and FOSSA scanning wired into CI. The
self-GTR's own admission that there was "no formal framework, security is
discussed during PR review" was honest but weak at the time. The more
important update is the DD issue's claim of a completed June 2025
third-party security review with tracked remediation, which is the
single biggest maturity change since the self-GTR was written.

**Q: Describe how the project has evaluated which features will be a security risk to users if they are not maintained by the project.**

The self-GTR's stated approach, that
every piece of code must be owned by a SIG or it can't land, is a
structurally sound answer, and I have no reason to doubt it's still
current given the SIG/[OWNERS_ALIASES](https://github.com/kubevirt/kubevirt/blob/main/OWNERS_ALIASES) model is unchanged.

**Q: Cloud Native Threat Modeling: explain the least minimal privileges required by the project and reasons for additional privileges.**

By design, a VM should never grant more privilege than the cluster already
allows a regular pod. `virt-handler` is the one deliberate, narrowly-scoped
exception.

**Q: Describe how the project is handling certificate rotation and mitigates any issues with certificates.**

Handled via a self-managed internal CA with a
configurable rotation interval and a documented manual force-rotation path
(delete the relevant Secret), a standard, reasonable pattern.

**Q: Describe how the project is following and implementing secure software supply chain best practices.**

This is a real gap. Signed
git tags and FOSSA/SonarCloud scanning exist, but I found no SBOM
published with releases and no image signing (no cosign/Sigstore use).
That's below where CNCF graduation-level expectations for supply-chain
security have moved; FOSSA and SonarCloud alone don't cover SBOM or
provenance.

On threat modeling specifically: the self-GTR said none had been done
formally. The completed third-party security review (June 2025, per the
DD issue) functionally covers that gap externally. Moderate/low findings
are reportedly tracked in a private Slack channel rather than a public
issue. That's weaker than typical CNCF transparency norms, even allowing
for the underlying report needing to stay embargoed for a while. A
public tracking issue or published summary would match the project's own
stated intent to publish the report.

## Day 1: Installation and Deployment Phase

### Project Installation and Configuration

**Q: Describe what project installation and configuration look like.**

Same operator + CR
pattern described above; consistently cross-referenced across docs.

### Project Enablement and Rollback

**Q: How can this project be enabled or disabled in a live cluster? Please describe any downtime required of the control plane or nodes.**

A single CR
create/delete, with no control-plane or node downtime required.
Enabling KubeVirt adds new controllers/CRDs alongside existing workloads
rather than modifying API server configuration.

**Q: Describe how enabling the project changes any default behavior of the cluster or running workloads.**

Existing (non-VM) workloads are unaffected;
KubeVirt only adds new resource types and controllers. The self-GTR's
framing here still holds.

**Q: Describe how the project tests enablement and disablement.**

Exercised as part of the
project's standard e2e suite, not a separate manual process.

**Q: How does the project clean up any resources created, including CRDs?**

The operator owns all subordinate
resources via owner references and finalizers, so deleting the `KubeVirt`
CR (or the operator manifest) tears everything down cleanly. This is the
correct Kubernetes-native pattern for teardown, not a bespoke uninstall
script.

### Rollout, Upgrade and Rollback Planning

**Q: How does the project intend to provide and maintain compatibility with infrastructure and orchestration management tools like Kubernetes and with what frequency?**

Concrete and falsifiable:
[`docs/kubernetes-compatibility.md`](https://github.com/kubevirt/kubevirt/blob/main/docs/kubernetes-compatibility.md) states each release supports the 3
most recent Kubernetes minors at time of cut, cross-published in a
support matrix in sig-release and rolled forward continuously on `main`.
More rigorous than the prose-only compatibility statements many CNCF
projects rely on.

**Q: Describe how the project handles rollback procedures.**

A genuine, disclosed limitation. The project is
upfront that it's "roll-forward only" by design, and that downgrade,
while technically possible, isn't a tested path.

**Q: How can a rollout or rollback fail? Describe any impact to already running workloads.**

Per
the self-GTR, a failed rollout leaves the Operator's "Ready" condition
false while running workloads keep running for a time; depending on the
failure, they may eventually be affected by cluster-wide ripple effects.
I have no independent evidence contradicting this, but also no evidence
of a rollback-specific failure drill having been run.

**Q: Describe any specific metrics that should inform a rollback.**

The Operator's
`Ready` condition being persistently false is the one signal called out;
no dedicated rollback-trigger metric or alert rule was found.

**Q: Explain how upgrades and rollbacks were tested and how the upgrade->downgrade->upgrade path was tested.**

Upgrade testing is part of
pre-submit CI. I found no CI job or test plan covering downgrades in the
current repo, so the self-GTR's admission that "rollbacks and
up→down→upgrade testing is not covered" is still accurate. For a project
managing live, stateful VM workloads, as opposed to a stateless
controller you can just scale to zero, an untested rollback path carries
more operational risk than it would for a stateless service. Whether
this has changed since the self-GTR was written is unconfirmed.

**Q: Explain how the project informs users of deprecations and removals of features and APIs.**

Sound, and matches the API
discipline noted above. The v1.9.0 changelog shows a properly
telegraphed deprecation (cgroup v1 support marked deprecated, removal
planned for a future release) rather than a silent removal. Removals of
stable-API constructs go through an opt-in FeatureGate and are discussed
on the dev mailing list first.

**Q: Explain how the project permits utilization of alpha and beta capabilities as part of a rollout.**

A
single release (v1.9.0) shows more than a dozen concrete feature-gate
graduations (WorkloadEncryptionSEV alpha→beta, PanicDevices→GA,
HotplugVolumes/DeclarativeHotplugVolumes→beta, MigrationPriorityQueue→GA,
VMExport→GA, Persistent Reservation→GA), strong evidence the
alpha→beta→GA model mirroring upstream Kubernetes is the project's
actual day-to-day practice, not a policy written for the application.

## Day 2: Day-to-Day Operations Phase

### Scalability/Reliability

**Q: Describe how the project increases the size or count of existing API objects.**

KubeVirt is a
controller-based extension leveraging core Kube entities at runtime,
roughly tens of pods, secrets, and a daemonset per cluster regardless of
scale, plus one additional pod (`virt-launcher`) per running VM. That
linear per-VM growth is the main driver of etcd/API-server load, not the
control plane itself.

**Q: Describe how the project defines Service Level Objectives (SLOs) and Service Level Indicators (SLIs).**

Still not defined at the project level. I couldn't find
an SLO/SLI document in kubevirt/kubevirt or kubevirt/community, and this
matches the self-GTR from 18 months ago. This is a genuine, unresolved
gap for Graduation-level operational maturity, not just an unanswered
question.

**Q: Describe any operations that will increase in time covered by existing SLIs/SLOs.**

N/A,
since no SLIs/SLOs exist to extend.

**Q: Describe the increase in resource usage in any components as a result of enabling this project, to include CPU, Memory, Storage, Throughput.**

Confirmed
as non-trivial but workload-dependent. The project recommends dedicated
infra nodes or reserved spare capacity, which is a reasonable operational
recommendation but not a quantified model.

**Q: Describe which conditions enabling / using this project would result in resource exhaustion of some node resources (PIDs, sockets, inodes, etc.)**

Since
every VM runs in its own pod, it inherits the same limits as any other
pod. There's no KubeVirt-specific exhaustion vector beyond what a
cluster operator would already plan for with a high pod-density workload.

**Q: Describe the load testing that has been performed on the project and the results.**

SIG Scale runs regular
performance/scale testing, and the v1.9.0 changelog references "release
1.8 perf-scale benchmarks data" as a real, versioned artifact, but it
isn't linked from the GTR or roadmap docs, so a reviewer has to know to
go looking for it in changelog entries. Worth asking the project to
surface that directly rather than leaving it buried.

**Q: Describe the recommended limits of users, requests, system resources, etc. and how they were obtained.**

The self-GTR's figures
("thousands of VMs on well under 100 nodes" for a typical large
deployment, "tens of thousands of VMs on hundreds of nodes" for
highly-optimized operators) are plausible given adopters like CoreWeave
and NVIDIA operating at that scale, but aren't backed by a reproducible,
published benchmark methodology in the main repo.

**Q: Describe which resilience pattern the project uses and how, including the circuit breaker pattern.**

No explicit circuit
breaker pattern is described or found in the architecture docs. Resilience
is instead achieved through standard Kubernetes primitives:
multi-replica control-plane Deployments with leader election, DaemonSet
node agents, and reconciliation loops that retry on failure. That's a
reasonable substitute but not a direct answer to the question as asked.

### Observability Requirements

**Q: Describe the signals the project is using or producing, including logs, metrics, profiles and traces. Please include supported formats, recommended configurations and data storage.**

Prometheus-format metrics and alerting rules with runbooks are shipped
and actively maintained. The v1.9.0 changelog alone adds several new
metrics (guest OS panic tracking, GPU info, VMI sync counts) and
deprecates others with migration guidance. No first-party tracing was
found; logs go through standard container stdout/stderr.

**Q: Describe how the project captures audit logging.**

Delegated to the Kubernetes audit log, since all
user-facing API calls go through the Kubernetes API server. KubeVirt
doesn't maintain a separate audit trail.

**Q: Describe any dashboards the project uses or implements as well as any dashboard requirements.**

None shipped as first-party; community-maintained Grafana
dashboards exist. Reasonable for an infra-extension project, but worth
noting it's not something the project itself curates or guarantees stays
current.

**Q: Describe how the project surfaces project resource requirements for adopters to monitor cloud and infrastructure costs, e.g. FinOps.**

No KubeVirt-specific FinOps tooling;
adopters are expected to monitor the underlying Kubernetes
resource usage KubeVirt consumes, same as any other workload.

**Q: Which parameters is the project covering to ensure the health of the application/service and its workloads?**

Workload health checks (liveness/readiness
probes) are configurable per VM, and the Operator surfaces its own and
its dependents' health via conditions and a Prometheus endpoint.

**Q: How can an operator determine if the project is in use by workloads?**

Since every VM
runs as a pod, standard pod-monitoring tooling already surfaces
KubeVirt-managed workloads. No separate discovery mechanism is needed
or provided.

**Q: How can someone using this project know that it is working for their instance?**

By checking Operator
conditions; if something is broken, a condition is set accordingly. This
is serviceable but coarse-grained compared to a proper health-check API.

**Q: Describe the SLOs (Service Level Objectives) for this project.**

Still none
defined. The "health" story is entirely condition-based rather than
SLO-based, which mirrors how Kubernetes itself handled component health
at a comparable stage of maturity. Not disqualifying, but unfinished.

**Q: What are the SLIs (Service Level Indicators) an operator can use to determine the health of the service?**

None formally
defined; Operator conditions are the closest available proxy.

### Dependencies

**Q: Describe the specific running services the project depends on in the cluster.**

Kubernetes only, as a hard
requirement; Containerized Data Importer and kubernetes-nmstate are
optional companions, not dependencies of the core install.

**Q: Describe the project’s dependency lifecycle policy.**

Go modules tracked via go.mod/go.sum,
with each addition vetted during PR review. No separate, written
dependency-lifecycle policy document exists beyond that review-time
practice.

**Q: How does the project incorporate and consider source composition analysis as part of its development and security hygiene? Describe how this SCA is tracked.**

FOSSA runs on every pull request for
license/security compliance, and SonarCloud is used periodically for
code-quality/security-pattern scanning.

**Q: Describe how the project implements changes based on source composition analysis (SCA) and the timescale.**

No
documented SLA exists for how quickly SCA-flagged issues must be
remediated (e.g., no "critical CVEs patched within N days" commitment).
This is a should-fix, and it's related to the SBOM/provenance gap flagged
under Security above.

### Troubleshooting

**Q: How does this project recover if a key component or feature becomes unavailable? e.g. Kubernetes API server, etcd, database, leader node, etc.**

If the Kubernetes control
plane is lost, existing VM workloads keep running and KubeVirt components
periodically attempt to reconnect. This is consistent with how a
controller/DaemonSet architecture actually behaves, and I have no reason
to doubt this given the `virt-handler`/`virt-controller` split
responsibility model.

**Q: Describe the known failure modes.**

Two are disclosed: loss of the cluster API
(workloads continue, control plane recovers once the API returns) and
loss of a node/kubelet (workloads on that node go down and are
rescheduled elsewhere where possible). Both are accurate, ordinary
consequences of the architecture rather than KubeVirt-specific surprises.

### Compliance

This section is new in the current template version and doesn't appear in
the project's Jan-2025 self-GTR at all.

**Q: What steps does the project take to ensure that all third-party code and components have correct and complete attribution and license notices?**

No documented answer exists yet. FOSSA scanning
covers license compliance at a high level, but that's not the same as a
documented attribution/notice process.

**Q: How are notices managed for third-party code incorporated directly into the project's source files?**

No documented answer yet.

**Q: How are notices retained for unmodified third-party components included within the project's repository?**

No documented answer yet.

**Q: How are notices for all dependencies obtained at build time included in the project's distributed build artifacts (e.g. compiled binaries, container images)?**

No documented answer yet. Given
KubeVirt ships multiple container images plus an OLM/CSV bundle, all
three of these attribution sub-questions should be explicitly asked of
the project rather than assumed. They simply haven't had the chance to
answer them in an updated GTR.

### Security (Day 2)

**Q: Security Hygiene: how is the project executing access control?**

Fully delegated to Kubernetes RBAC,
